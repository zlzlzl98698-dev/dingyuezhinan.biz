在 128MB 至 256MB 内存的低配硬路由或老旧软路由上选型时，如果固件版本达到 OpenWrt 23.05 及以上且机场提供 sing-box 格式或精简通用配置，优先推荐选择 **HomeProxy**；如果路由器刷的是老版本固件、手头仅有一条通用 V2Ray 链接，或者需要细致的局域网单设备访问控制界面，则建议选用裁剪过核心与规则文件的 **PassWall2**。无论最终选用哪一款，低内存设备稳健运行的核心前提都是严控节点数量、精简分流规则数据库并避开高并发全量测速。

在 OpenWrt 生态中，功能极其丰富的 OpenClash 一旦加载完 Mihomo 核心和庞大的规则集，常态内存开销往往就会吃掉上百兆空间，这在 1GB 内存以上的 x86 软路由上不算什么，但放在 128MB 或 256MB 内存的家用嵌入式路由器上极易引发频繁重启甚至连不上 Wi-Fi。关于整个 OpenWrt 插件矩阵的宏观对比，可先阅读 [OpenWrt 软路由全组件分析](/clients/openwrt-clients/) 与 [OpenWrt 装机前必核参数](/clients/openwrt/)。

## 低内存环境下两款插件的资源开销与底层对比

在内存寸土寸金的嵌入式路由器上，除了看代理软件界面好不好用，更要拆解它占用了多少 Flash 闪存空间以及运行时会吃掉多少 RAM 运行内存。

| 评估维度 | HomeProxy（原生现代体系） | PassWall2（多核心成熟体系） |
| :--- | :--- | :--- |
| 底层核心与包体积 | 单一锁定 `sing-box` 核心，界面脚本极度轻量 | 可调用 `Xray` 或 `sing-box`，依赖组件相对较多 |
| 固件与防火墙门槛 | 要求 OpenWrt 23.05+ 与原生 `fw4`（nftables） | 兼容广，老旧 `fw3`（iptables）及新版 `fw4` 均能适配 |
| 规则集内存友好度 | 采用紧凑二进制 `.srs` 规则集，按需加载极省内存 | 若采用传统大体积 `geosite.dat` 文件，加载瞬间内存峰值高 |
| 订阅与操作友好度 | 界面偏向原生态工程选项，适合标准订阅或单节点管理 | 中文引导生态成熟，分流组、节点测试与访问控制极顺手 |
| 对低内存设备的包容度 | 在 256MB 内存环境下运行极为宽松，128MB 可做极简配置 | 256MB 内存运行稳健，128MB 需严格关闭冗余核心与大规则 |

### 为什么 HomeProxy 在 23.05+ 新固件上更省内存

HomeProxy 彻底丢弃了早期 LuCI 插件依赖多层 Shell 拼装、重复启动辅助脚本以及引入多种冗余工具包（如独立测速器、复杂统计模块）的习惯，它几乎完全依托 OpenWrt 原生框架与单一 [sing-box 核心](/clients/sing-box/) 运行。

尤为关键的一点在于规则文件的加载机制。传统内核加载一次包含几万条域名和 IP 段的完整 `.dat` 路由库时，反序列化到内存中会瞬间制造出一个远超文件本身大小的内存峰值，这正是无数小内存路由器“刚点启动按钮就直接掉线重启”的罪魁祸首。sing-box 的现代规则集按二进制扁平结构设计，配合 HomeProxy 克制的功能开关，在 256MB 内存机器上能把代理进程常态占用稳稳压在一个非常安全的区间内。

### PassWall2 在特定低配老固件上的不可替代性

虽然 HomeProxy 足够干净轻量，但它无法运行在大量还停留在 OpenWrt 21.02 或 22.03 甚至部分厂商魔改老 SDK 的硬件设备上。对于这类无法升级到最新系统内核的设备，PassWall2 依然是可靠选择。

如果打算在 256MB 或更紧巴巴的设备上使用 PassWall2，选型和安装阶段必须做减法。首先是核心包二选一，不要同时把 Xray 和 sing-box 两个庞大的可执行文件都塞进只有 32MB 或 64MB 的路由器闪存里，看清自己主力机场用的协议，如果机场全节点是 VLESS/VMess/Trojan，单独只装轻量化的 `Xray` 核心包即可；如果包含了 Hysteria 2，则只保留 `sing-box`。其次是谨慎选择组件内的规则分类，千万不要随手勾选所有冷门国家规则或上万条广告拦截库，仅保留核心直连分流就足够日常使用。

## 拯救低内存路由器的四条关键调优准则

硬件内存不够用时，哪怕选对了插件，错误的配置习惯一样会把路由器拖垮。在低内存设备上部署透明代理，务必落地下面四项保命习惯。

### 第一步 删减订阅中的无效节点并停用循环自动测速

很多机场的订阅列表里包含几十甚至上百条不同倍率、不同地区的节点，其中大部分日常根本不会点击连接。对于低内存路由器，导入全量上百个节点不仅会在配置文件解析阶段拉爆内存，而且一旦在界面开启了“定时自动节点测速”，几十个并发探测连接同时打向路由器本就瘦弱的 CPU 和有限的连接跟踪表（conntrack），直接会导致内网正常网页卡顿。建议在机场后台或导入时利用关键字过滤，只留十个以内最常用的高速低延迟节点，并始终保持手动按需测速。

### 第二步 关闭无用的日志记录与连接监控面板

部分用户习惯长期开着详细的流量追踪、连接日志甚至抓包统计功能。在手机或电脑上这不算负担，但在依靠 Flash 闪存和极小内存维持运转的路由器上，持续刷新的日志缓存如果直接写进虚拟内存盘（`/tmp`），不出一天就会把剩余可用 RAM 彻底塞满。部署稳定后，把运行日志级别调整为仅记录致命错误或直接关闭详细审计输出。

### 第三步 确认系统交换空间（Swap）或外部挂载辅助

如果你的路由器自带 USB 接口且插着闲置 U 盘，在确定使用稍微重一点的分流插件时，可以为固件划分一个小容量的外部存储与轻量 Swap 缓冲，不过要清楚 U 盘读写远慢于物理内存，它只能作为避免突发峰值直接死机的安全气囊，不能靠它来强行跑超出硬件能力几倍的大型策略组。

### 第四步 分清需求边界避免把主路由拖垮

对于依然还在服役的 128MB 内存甚至 64MB 内存超老旧硬路由，如果实在找不到匹配的稳定固件或者每次更新订阅都濒临死机，最理性的工程决策不是硬往路由器里塞代理插件。完全可以让老路由器安安静静负责有线和无线物理转发，把代理运算交给性能充裕的个人电脑、手机客户端（例如 [v2rayN](/clients/v2rayn/) 或 [Clash Verge Rev](/clients/clash-verge-rev/)），或者另外购置一台廉价小巧的二手 ARM/x86 机器作为专职旁路由，彻底消除全家断网隐患。关于多设备架构组合及机场第三方订阅支持范围，可以配合查阅 [多设备接入指南](/guides/multi-device-setup/) 与 [机场客户端兼容性核对](/clients/proprietary-vs-third-party/)。
