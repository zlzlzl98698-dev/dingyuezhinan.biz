同一个机场在两个客户端里测出的延迟数字相差数倍甚至十几倍，核心原因在于不同客户端默认采用的测速协议层级、探测目标网址和并发逻辑完全不同。部分软件默认执行的是本地到国内中转入口的 `TCPing`（只测前半段路程），而另一部分软件执行的是穿过整条代理隧道访问海外网页的 `URL-Test`（测量端到端真实首包响应），两者测量的根本就不是同一段网络行程。

要看懂这些相差悬殊的毫秒数到底哪一个更接近真实上网体验，必须把测速机制拆成四个层级来对照。如果你经常对照评测图表挑节点，建议一并查看 [怎么看懂 MiaoKo 测速图](/guides/how-to-read-miaoko-speedtest/) 与 [延迟与带宽指标解析](/network/bandwidth-latency/)。

## 四种延迟口径拆解 你看到的毫秒数测到了哪一步

在常见代理软件（如 Clash Verge Rev、v2rayN、Shadowrocket 和专业测速工具 MiaoKo）中，屏幕上显示的毫秒数通常对应下面四类机制中的一种。

| 测速方式名称 | 实际测量区间 | 包含环节 | 典型数值特征（以香港节点为例） | 对真实上网体验的参考价值 |
| :--- | :--- | :--- | :--- | :--- |
| ICMP Ping | 本机到节点入口 IP | 仅网络层往返，不走代理协议 | 10ms 至 35ms | 极低，完全无法判断节点服务端是否存活 |
| TCPing（真连接前段） | 本机到国内中转机端口 | 仅 TCP 三次握手 | 15ms 至 40ms | 仅能看出国内入口近不近，测不出跨境线是否拥堵 |
| TLS RTT | 本机穿过节点到目标服务端加密层 | 代理隧道转发加 TLS 握手往返 | 20ms 至 80ms | 较高，能反映中转到落地机器的链路质量 |
| HTTPS 延迟（URL-Test） | 本机经代理访问目标测速网址完整响应 | 隧道握手、DNS 解析加 HTTP 204 首包返回 | 90ms 至 350ms | 最高，最贴近点开网页和等待 AI 吐字的首响等待 |

最容易让新手产生错觉的，就是把“中转入口 TCPing”误当成“整条代理线的真实速度”。很多商业机场在国内部署了广东、上海或北京的高防中转机，不管你用电脑测试哪个国家的节点，只要客户端运行的是 TCP 端口连通测试，测出来的全都是你家宽带到广东或上海那台入口机的 25ms 延迟。哪怕那台香港或美国落地机此时已经断网宕机，只要入口机端口还开着，TCPing 依然会绿油油地显示 25ms。

## 真实实测数据里的“低 RTT 与高 HTTPS 延迟”背离

不要以为只有跨软件才会有差距，即便在同一个专业测速平台里，把加密层往返时间（TLS RTT）和真实 HTTPS 请求延迟摆在一起对比，也经常能看到触目惊心的背离现象。

对照 `benchmarks.json` 收录的 [光速云](/reviews/guangsuyun/) `2026-08-19` 河北联通 2Gbps 后端 62 节点实测原图，就能找到极其典型的现场证据。在河北联通的测试环境下，同一份 Shadowsocks 订阅中的 `香港专线 07` 测出的 `TLS RTT` 只有 66ms，看似响应极快且平均下载速度达到 35.93MB/s；但往旁边一列的 `HTTPS 延迟` 看去，数字却暴涨到了 **1235ms**。同批测试里，`日本 07` 的 HTTPS 延迟达到了 **1879ms**，`台湾 05` 达到 **1542ms**，`新加坡 06 至 09` 全部落在 **1296ms 至 1432ms** 区间。与此同时，同一张表里的 `香港专线 18` 的 HTTPS 延迟只有 210ms，`香港专线 05` 为 248ms。

为什么会出现 66ms 的底层 RTT 却拖出 1235ms 的上层网页响应？原因通常集中在跨境段丢包重传、特定运营商路径上的 QoS 队列拥塞，或者落地节点远端解析目标测速域名耗时过长。在实际使用中，如果你选了 `香港专线 07` 去刷图片很多的网页或和 ChatGPT 对话，每一次点击都要白白等待超过一秒才会开始加载内容，体感远不如 `香港专线 18` 顺畅。而只测 TCPing 或单看 RTT 的客户端根本不会向你发出警告。

## 同为 URL-Test 为什么不同软件结果依然不同

哪怕两款客户端都明确开启了“真连接延迟测试（URL-Test）”，跑出来的数值依然可能差出几十到上百毫秒，背后主要受以下四个具体参数影响。

1. **默认测速目标网址不同**。Clash 系软件常用 `http://www.gstatic.com/generate_204` 或 `cp.cloudflare.com`，部分客户端则默认使用 `https://www.google.com` 或 `https://www.youtube.com`。如果测速目标是 `http://` 协议的 204 接口，它不需要在落地机和目标网站之间额外跑完一次完整的 HTTPS TLS 握手，测出来的数字自然比请求 `https://www.youtube.com` 少掉一个完整的远端握手往返（RRT），往往低出 80ms 到 200ms。
2. **冷启动 DNS 解析与连接复用机制差异**。第一次对某个冷门节点发起测试时，代理服务器需要现场向其上游 DNS 查询目标测速域名并建立全新 TLS 会话，这会把首次测量值拉高一倍以上。有些客户端支持测前预热或只取二次请求平均值，另一些客户端直接记录首次冷启动总耗时，两者面板数字必然差一大截。
3. **批量测速的并发数挤压本地链路**。部分客户端一键点“测试全部延迟”时，瞬间同时对 60 到 100 个节点并发建连，家用光猫或老旧路由器遇到这种突发海量连接很容易触发 NAT 表拥塞或 QoS 限流，导致排在列表后面的节点普遍多出几百毫秒排队延迟，甚至直接假超时。具体超时排查可看 [节点超时故障排查](/troubleshooting/node-timeout/)。
4. **本地 IPv6 干扰与协议实现差异**。如果在测速网址上刚好存在本地 DNS 优先返回了 IPv6 地址，或者同一机场在不同格式客户端下分别拉取了 Shadowsocks 组与 VLESS 组（在协议握手开销、TLS 复用和 AnyTLS 握手流程上本身就有差别），测出的首包时间也会各自浮动。

## 日常选节点的正确测速动作

既然知道了毫秒数背后的口径差异，日常在 [Clash Verge Rev](/clients/clash-verge-rev/)、[v2rayN](/clients/v2rayn/) 或 [Shadowrocket](/clients/shadowrocket/) 里挑选主力节点时，建议养成三个实用习惯。

首先，在客户端设置里统一使用真连接（URL-Test）测试，把测速地址明确设为通用的 `https://cp.cloudflare.com/generate_204` 或 `https://www.gstatic.com/generate_204`，关掉无意义的纯 ICMP Ping 测速，避免被入口假低延迟误导。其次，测速不要迷信一键全量狂刷，先按地区筛选出常用的 5 到 10 个节点单独点测两遍，取第二遍连接预热后的稳定 HTTPS 数值做对比。最后，一旦某个节点在客户端里显示正常绿色延迟但打开网页依然明显发顿，记得参考 [慢速与卡顿排查](/troubleshooting/slow-speed/) 直接切到同地区的相邻编号节点，或者在策略组里手动淘汰高 HTTPS 延迟的编号。
