代理客户端测试节点延迟时出现成片 `Timeout`（超时），不要急着卸载重装软件，也不要立刻怀疑机场跑路。最快定位节点超时原因应当按三个优先方向依次排查，第一优先核对设备本机系统时间与标准时间的误差是否超出 60 秒握手窗口，第二优先通过切换手机移动热点交叉验证是不是校园网、企业内网或宽带路由器阻断了节点端口与 UDP 流量，第三优先在关闭本地代理的前提下刷新订阅拉取新入口、排查账户配额以及核验客户端内核是否支持最新协议字段。按这三步走完，绝大多数成片超时都能在几分钟内精准定界。

## 节点超时现象与根因定位对照表

不同范围和不同协议的超时往往对应截然不同的网络层故障，可以先对照下表直接锁定重点检查方向。

| 超时范围与特征 | 对应根因层 | 验证命令或排查动作 | 修复优先级 |
| --- | --- | --- | --- |
| 重启或切双系统后全节点突然超时 | 本机系统时钟偏差超过协议容忍窗口 | 对比网络标准时间并运行时间同步命令 | 第一优先级 |
| 换手机热点立刻变绿，连 Wi-Fi 就全红 | 局域网、校园网或公司防火墙封锁端口 | 断开 Wi-Fi 改连移动数据测试同节点延迟 | 第二优先级 |
| 仅 Hysteria 2 超时，VLESS 或 Trojan 正常 | 当前运营商或内网拦截或限速 UDP 流量 | 用本地测速与切换 TCP 类节点交叉验证 | 第二优先级 |
| 长期未更新订阅导致全部老节点超时 | 服务端已更换中转入口域名或端口 | 关掉代理后刷新订阅并对照官方公告 | 第三优先级 |
| 仅新版 Reality 或 AnyTLS 节点报超时 | 客户端底层核心版本过旧无法握手 | 核对客户端核心版本及读取运行报错日志 | 第三优先级 |
| 测速全部超时但手动选中节点能打开网页 | 客户端默认测速 URL 在当前网络不可达 | 把测速 URL 换为 Cloudflare 204 检测地址 | 第三优先级 |

## 方向一 核查设备系统时钟与加密握手时间窗

在所有节点同时超时的案例里，本地时间漂移是最容易被忽略、却又命中率极高的一类故障。

### 为什么差两分钟就会全线断连

包括 VMess、Trojan、VLESS 以及衍生 TLS 传输在内的现代代理协议，为了防止历史数据包被恶意截获后重放攻击，都会在加密认证握手阶段强制校验客户端与服务端之间的绝对 UTC 时间戳差距。服务端通常只允许 **60 到 90 秒** 的时钟窗口，一旦你电脑或手机上的时间比标准时间快了或者慢了超过两分钟，远程服务器在解析握手报文后会直接静默丢弃数据包，不返回任何错误提示，客户端界面上表现出来的就是全部节点死等到底，最终清一色报出 `Timeout`。

### 三类高发时间漂移场景与命令同步

在日常使用中，以下三类设备极易悄悄发生时钟跑偏。第一，同一台电脑同时安装了 Windows 与 Linux 双系统，由于两个系统对主板硬件时钟（RTC）是按本地时间还是 UTC 读取存在认知差异，每次来回重启切换经常直接错差整整八个小时；第二，使用多年的老旧台式机主板 CMOS 纽扣电池电量耗尽，或者长时间断电后重新开机时间退回到了出厂年份；第三，跨境出差或运行虚拟机时修改过系统时区，却没有打开自动网络对时。

Windows 用户可以右键桌面右下角的时间区域点击调整日期和时间，开启自动设置时间并点击立即同步；macOS 进入系统设置的日期与时间开启自动设置；Android 与 iPhone 同样开启自动确定日期和时间。如果系统界面按钮提示同步超时，直接在终端用命令行强制校时更彻底。

```powershell
# Windows 管理员 PowerShell 检查当前时间偏差并强制向标准时间服务器同步
w32tm /query /status
net start w32time 2>$null
w32tm /resync /force
```

```bash
# macOS 终端强制向苹果时间服务器校准系统时钟
sudo sntp -sS time.apple.com

# Linux（systemd-timesyncd）查看时间同步状态并启用 NTP 自动对时
timedatectl status
sudo timedatectl set-ntp true
```

时间同步拉回正常误差范围之后，务必重启一次代理客户端或底层核心进程，再重新点一次全部测速，很多全红页面往往当场恢复成一排绿灯。

## 方向二 隔离验证本地宽带、校园网与公共网络拦截

如果确定设备时钟误差在几秒以内，接下来最关键的动作是判断故障究竟发生在自己的局域网环境，还是出在机场节点那头。

### 用手机移动热点做三分钟网络隔离测试

不同网络接入环境对出站连接的限制差异极大。高校校园网、酒店免费无线网络、机场车站公共 Wi-Fi 以及设置了上网行为管理系统的企业办公内网，常常会封锁除 `80` 和 `443` 之外的绝大多数非常规高位端口，部分策略甚至会直接丢弃高频 UDP 数据包。由于诸如 Hysteria 2 这类现代协议默认依赖基于 UDP 的 QUIC 传输，一旦进入封杀 UDP 的公司或校园 Wi-Fi 环境，就会表现得像节点彻底掉线一样全部超时。

判断是不是当前网络在搞鬼，最干脆的办法就是拔掉网线或断开公司 Wi-Fi，打开手机移动数据个人热点让电脑连上去再测一次节点延迟。

1. 如果切到手机 4G 或 5G 热点后节点瞬间亮起几十毫秒绿灯且能流畅打开海外网页，证明机场节点完全健康，问题百分百出在原来的宽带光猫、路由器或者校园网防火墙策略上。此时在原网络环境下可以优先改用走标准 `443` 端口的 VLESS 或 Trojan 节点，避免在受限内网硬连大端口或纯 UDP 线路。
2. 如果切到手机移动热点后，依然全线超时没有任何改善，即可彻底排除家里和公司局域网的锅，继续进入下一阶段的订阅、账号与客户端排查。

### 使用终端网络命令探测入口端口与 DNS 连通性

当发现节点超时，但不确定是节点域名根本没解析出 IP，还是 IP 通了却被中间防火墙掐断了端口握手，可以结合客户端的运行日志与系统端口探测命令快速定界。注意在测试节点入口域名时使用公开或本地占位地址，切勿把真实的机场内部域名和 Token 泄露给无关第三方。

```bash
# 1. 检测本地到节点入口域名的 DNS 解析是否正常（若解析不出或返回保留地址则需查 DNS）
nslookup node-entry.example.invalid

# 2. Windows PowerShell 探测节点端口 TCP 握手是否能建立（把端口替换为节点实际端口）
Test-NetConnection -ComputerName node-entry.example.invalid -Port 443

# 3. macOS / Linux 快速探测 TCP 端口连通性
nc -vz -G 5 node-entry.example.invalid 443
```

如果 `Test-NetConnection` 或 `nc` 连基础 TCP 握手都卡死超时，说明在当前网络环境下这条中转入口 IP 或端口已经遭到阻断，或者服务器正在离线维护；如果端口本身一秒连上，客户端依然显示超时，那多半是代理软件内部的 TLS 参数、UUID 凭证失效或者本地端口冲突所致，需要进一步结合 [代理连接不上排查](/troubleshooting/connection-failed/) 与 [DNS 错误排查](/troubleshooting/dns-error/) 核对本机代理监听状态。

## 方向三 刷新订阅入口、排查账号状态与软件核心版本

排除了时钟和本地网络拦截，全线超时就集中在配置陈旧、账号停权以及客户端兼容性三个层面。

### 直连状态下更新订阅并检查套餐配额

如果你已经有好几周甚至几个月没更新过节点列表，服务商很可能因为上游机房切换或线路优化早就更换了新的中转入口 IP 与端口，你本地软件里还存着已经下线的老地址，测速当然全部超时。在更新订阅前，**务必先关闭系统代理和 [TUN 虚拟网卡模式](/guides/tun-mode/)**，让客户端在直连状态下重新拉取一次配置。如果直连拉取报错，可继续参考 [订阅更新错误排查](/troubleshooting/subscription-update-failed/) 处理。

另外，账号流量彻底耗尽、套餐正好在昨晚到期，或者同时在线设备数超过限制触发后台防分享踢线，服务器同样会断开认证使所有节点表现为 Timeout。直连登录官网用户面板核对一下剩余天数、剩余流量与封控提示，若确认长期大面积停摆且官网一并打不开、工单长期无人回复，则需高度警惕 [品牌运营异常](/risks/operational-issues/) 并及时启用备用方案。

### 区分真超时与测速链接或旧内核引发的假超时

还有两种非常容易误判的伪超时场景。第一，部分客户端默认内置的延迟测试地址（例如 `http://www.gstatic.com/generate_204`）偶尔在个别线路或局部解析上产生波动，可以在 [Clash Verge Rev](/clients/clash-verge-rev/) 或 [v2rayNG](/clients/v2rayng/) 设置里把测速链接替换为 `https://cp.cloudflare.com/generate_204`，或者直接选中一个节点打开浏览器实测网页能不能加载；第二，如果列表里老旧 Shadowsocks 节点全绿可用，偏偏所有 VLESS Reality、AnyTLS 或 Hysteria 2 新节点清一色报错超时，说明客户端内核版本太老了，去官方仓库升级新版即可，详见 [客户端兼容性问题排查](/troubleshooting/client-compatibility/)。

## 常见问题解答

### 为什么电脑改过双系统或者长时间没联网后，所有节点突然全部超时

Windows 与 Linux 双系统对主板硬件时钟的读取标准不同，切换重启后本地系统时间常常整整偏离八小时；长期没通电的台式机也可能因为主板电池耗尽而时钟归零。主流加密协议严格校验 60 到 90 秒以内的时间戳误差，时间一偏服务端就会直接拒接导致全部节点显示 Timeout，执行一次自动同步时间即可解决。

### 客户端里测速显示 Timeout 超时，是不是一定代表节点已经彻底挂了

不一定。除了节点服务器本身下线维护，本机时间偏差、校园网或企业内网拦截非常规端口、同机运行了冲突的游戏加速器、或者客户端默认测速 URL 被局部干扰，全都会让延迟显示为超时。用手机热点测一次以及打开浏览器直连验证，能立刻分辨出节点是真挂还是假超时。

### 只有某几个节点超时，其他地区的节点正常连着，怎么处理

单地区或少数编号节点超时大多属于该机房入口正在临时扩容维护、遭遇阶段性跨境拥堵或者局部 IP 波动。先在直连状态下点一次更新订阅看看服务商是否已经下发了替换节点，如果依然超时则暂时切到同套餐下其他地区的可用节点（比如从香港临时换到新加坡或日本），等待机房恢复即可。

### 怎么从内核日志一眼看出节点超时到底是卡在 DNS 还是卡在握手阶段

打开客户端的实时日志面板并把日志级别调到 `info` 或 `debug`，再次发起一次测速或访问网页。如果日志里卡在域名解析报错或持续重复 `resolve failed`，问题在 DNS；如果顺利拿到了目标 IP 却连续报 `i/o timeout`、`context deadline exceeded` 或 `TLS handshake timeout`，则说明网络链路到目标端口的握手被阻断或节点本身已离线。
